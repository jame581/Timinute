# v2.5 — Server-side Timer, Timer Notifications, Aurora Dialogs — Design

_Date: 2026-11-14. Status: draft for review. Scope and approach chosen by Jan in the project thread on 2026-11-14. Builder-checked; its findings are folded in, and every choice marked "My call" is open to change._

## Why

The roadmap's P1 **Notifications** item has had a placeholder bell in the topbar since v2.1. The most useful first slice is a set of warnings about the timer: "your timer has been running for 9 hours" and "you've been idle for 15 minutes while tracking".

While reading the code, I found that these warnings can't be reliable today. A running timer only exists in one browser tab:

- `TimeTracker.razor` → `StartTracker()` POSTs a `TrackedTask` with a **1-second placeholder `Duration`**. The fact that it is running is stored only in that tab's `sessionStorage` (`"trackedTask"`).
- If you close the tab while the timer runs, the session is gone. The server keeps a 1-second task, and the tracked time is **silently lost**.
- Another tab, or another device, cannot see that a timer is running.
- So any "you left it running" warning could only fire inside the same tab that would have lost the data anyway.

v2.5 therefore makes the running timer a server-side fact first, then builds the notifications on top of that. It also ships two smaller items that were already agreed: Aurora-native dialogs and dependency hygiene.

## Goals

1. **The timer survives the tab.** Starting a timer records it on the server. Reloading, closing the tab or switching devices shows the same running timer, and stopping it from anywhere produces exactly one correct `TrackedTask`.
2. **Long-running timer warning.** Once a running timer passes a user-configurable threshold, the bell shows a warning, and an opt-in browser notification fires on devices where it is enabled.
3. **Idle warning with a fix-up action.** If no keyboard or pointer activity is seen for N minutes while a timer runs, the user is told when they returned and offered **"Stop at <idle start>"** (the idle time is discarded) or **"Keep"**.
4. **The bell works.** Clicking it opens a small Aurora popover listing the active timer warnings, with actions. The badge shows the count.
5. **Aurora-native dialogs** replace the Radzen Material `DialogService` dialogs, so they no longer render white and bright blue in dark mode.
6. **Hygiene:** dependency bumps on develop, Dependabot retargeted to `develop`, and the docs bookkeeping caught up.

## Non-goals (v2.5)

- **Web Push / notifications while the app is closed.** These would need VAPID keys in every self-hoster's config and would route notification payloads through browser-vendor push services. That conflicts with the self-host pitch. Notifications fire only while at least one Timinute tab is open.
- **A persisted notification inbox / history.** Every v2.5 notification can be derived from the current timer state and preferences, so there is no `Notification` table.
- **SignalR / real-time push between tabs.** Polling plus refetch-on-focus is enough (see Client design).
- **Task reminders, Pomodoro, estimates, break tracking.** These are the rest of the P1 items and are v2.6 candidates.
- **MCP `start_timer` / `stop_timer` / `get_running_timer` tools.** The new `TimerAppService` makes them cheap, but they are a separate feature with their own scope and audit implications. They are a v2.6 candidate, and possibly a good follow-up announcement hook.
- **Cleaning up old 1-second orphan tasks** already in users' databases. They can't be told apart from real 1-second entries reliably. Users can delete them.
- **Editing the name or project while the timer runs.** Today's UI disables those fields while running; v2.5 keeps that behaviour.

## Anti-goals

- A running timer must never show up in analytics, exports, calendar, search or MCP results as a half-finished task. That is the main reason for the entity choice below.
- No data leaves the server for notifications. There are no third-party services.
- Nothing regresses for users who never enable browser notifications. The bell alone carries every warning.

## Approaches considered (timer state)

| Approach | Trade-off | Verdict |
|---|---|---|
| **A. Client-only watcher** over the existing sessionStorage timer | Smallest change. Keeps the lost-time bug, and warnings only work in one tab. | Rejected by Jan |
| **B. Server-side running timer + bell + opt-in browser notifications** | A migration plus a new endpoint group. Fixes data loss, works across devices, and unlocks MCP timer tools later. | **Chosen** |
| **C. B + Web Push** | Reaches users with the app closed, but adds per-install VAPID config and third-party push routing. | Rejected (non-goal) |

### Sub-decision: how to store "running" (my call)

| Option | Trade-off |
|---|---|
| **B1. Nullable `EndDate` / `IsRunning` flag on `TrackedTask`** | No new table. But **every** aggregate, export, search, calendar query and MCP tool must remember to exclude running rows, and `Duration` is meaningless while running. That makes it easy to regress (see anti-goal 1). |
| **B2. A separate `RunningTimer` entity, one row per user; stopping it creates the `TrackedTask`** | One new small table. Existing queries are untouched because a running timer is simply not a `TrackedTask` yet. The one-per-user rule is enforced by the primary key. |

**Chosen: B2.** Stopping the timer goes through the existing `TimeEntryAppService.LogAsync` path, so ownership, `ProjectId` normalization and validation stay in one place. This follows the repo's FK-hardening rules in CLAUDE.md.

## Server design

### Entity: `RunningTimer`

```csharp
public class RunningTimer
{
    public string UserId { get; set; } = null!;          // PK + FK → ApplicationUser (cascade delete)
    public ApplicationUser User { get; set; } = null!;
    public string Name { get; set; } = null!;            // same length limit as TrackedTask.Name
    public string? ProjectId { get; set; }               // validated against caller ownership on start
    public DateTimeOffset StartDate { get; set; }        // UTC, server clock
}
```

- **The PK is `UserId`**, so at most one running timer per user. A second start returns 409.
- `ProjectId` is **not** an EF FK to `Project`. If the project is soft-deleted or purged while the timer runs, stopping it must not fail. `TimerAppService.StopAsync` checks the project itself **before** calling `LogAsync`. If the project is no longer owned or live, it passes `ProjectId = null` and returns `projectCleared: true`, so the client can show a note. `LogAsync` keeps throwing `ProjectOwnershipException` for REST and MCP callers; its behaviour is unchanged.
- It is **not soft-deletable** and has no query filter. A discarded timer is just deleted.
- It needs a migration via `scripts/AddMigration.ps1` (`AddRunningTimer`) in PR 2.

### `TimerAppService` (in `Server/Services/App/`, mirroring the existing `*AppService` pattern)

| Method | Behaviour |
|---|---|
| `GetAsync(userId)` | Returns the caller's `RunningTimerDto` or null. |
| `StartAsync(userId, StartTimerDto)` | Validates the name (required, trimmed, length) and `ProjectId` (whitespace → null, `Trim()`, must belong to the caller and not be deleted). Sets `StartDate = UtcNow` (server clock; the client does not send a start time). Inserts the row. Returns 409 if one exists (a unique-key violation is also mapped to 409 for the race between two tabs). |
| `StopAsync(userId, StopTimerDto)` | Loads the caller's timer (404 if none). `EndAt` is optional and defaults to `UtcNow`; if supplied (idle trim), it must satisfy `StartDate < EndAt <= UtcNow + 5s skew`, else 422. Durations under 1 s are clamped up to 1 s, because `MinDuration` rejects 0 (matching today's behaviour). Calls `TimeEntryAppService.LogAsync` with `{Name, ProjectId, StartDate, Duration = EndAt − StartDate}` and deletes the timer row inside **one explicit DB transaction** (`Database.BeginTransactionAsync`), so a stop can never create two tasks or lose the timer. A transaction is needed because `BaseRepository.Insert` saves immediately, so the two writes can't share one `SaveChanges`. *(My call: wrap in a transaction rather than changing the shared `LogAsync`, so the REST and MCP paths are untouched.)* Tests for this must use the SQLite helper, since InMemory ignores transactions. Returns the created `TrackedTaskDto`. |
| `DiscardAsync(userId)` | Deletes the caller's timer without creating a task. 404 if none. |

### `TimerController`

`[Authorize]`, `[Route("[controller]")]`, `[ResponseCache(NoStore = true)]`. Every action is scoped to the authenticated user id. There are no route ids at all, so nothing can address another user's timer.

| Endpoint | Result |
|---|---|
| `GET /Timer` | 200 `RunningTimerDto` or 204 when nothing is running |
| `POST /Timer/start` | 201 `RunningTimerDto` / 409 / 422 |
| `POST /Timer/stop` | 200 `StopTimerResultDto { TrackedTask, ProjectCleared }` / 404 / 422 |
| `DELETE /Timer` | 204 / 404 |

A successful stop is a non-GET, so the existing `AnalyticsCacheInvalidationHandler` clears the client analytics cache automatically. Start and discard also clear it, which is harmless.

### Preferences

Two new columns on the owned `UserPreferences`. *My call:* they get **their own migration** (`AddTimerNotificationPreferences`) in PR 3, where they are first used, so PR 2 stays focused on the timer:

| Field | Type | Default | Meaning |
|---|---|---|---|
| `LongTimerWarningHours` | `decimal(4,1)` | `8.0` | Warn once a running timer exceeds this. `0` = off. Range 0–24. |
| `IdleWarningMinutes` | `int` | `15` | Idle threshold while a timer runs. `0` = off. Range 0–240. |

These are exposed through the existing preferences GET/PUT DTOs with range validation (422 on violation).

**My call on defaults:** I used 8.0 h rather than reusing `WorkdayHoursPerDay`, because they mean different things: a target versus an "is this a mistake" signal. Jan can adjust these if they don't match real use.

The browser-notification opt-in is **per device**, so it lives in `localStorage` (`timinute.notifications.browser`), not on the server. Browser permission is per origin and per device anyway.

## Client design

### `TimerService` (singleton, `Client/Services`)

This is the single source of truth for timer state on the client. It replaces the sessionStorage logic in `TimeTracker.razor`.

- `Current` (`RunningTimerDto?`), `Elapsed` (computed from `StartDate` and the local clock), and a `Changed` event.
- `RefreshAsync()` calls `GET /Timer`. It runs on app start (after auth), **every 60 s while the app is visible**, and on `visibilitychange → visible` / window focus. That covers "stopped it on my phone, laptop tab still says running" within a minute or on focus.
- `StartAsync`, `StopAsync(endAt?)` and `DiscardAsync` call the API, then update `Current` and raise `Changed`. A 409 on start means another tab or device started a timer: refresh and show "A timer is already running".
- **One-time legacy migration:** if a v2.4 `"trackedTask"` sessionStorage entry exists on load, stop that placeholder task the old way (PUT with `EndDate = now`), which preserves exactly what v2.4 would have recorded. Then remove the key. The code path can be deleted in v2.6.

**Discarding a running timer (new UI).** Today you can't: the tracker's Reset button is disabled while running. *My call:* enable Reset while running and make it **Discard timer**. It asks for confirmation ("Discard 1h 12m of tracking?") and calls `DiscardAsync`. Until PR 4 lands, it uses the existing confirm; PR 4 migrates it to the Aurora confirm with the rest.

The tick for the live display stays a per-page `System.Timers.Timer` on `TimeTracker`, reading `TimerService.Elapsed`. The topbar also shows a compact running indicator (dot plus elapsed time, desktop only) so that a timer is visible from every page. **My call:** that indicator is small and makes the cross-page warnings make sense, but it can be cut if Jan doesn't want it.

### `TimerNotificationService` (singleton)

It subscribes to `TimerService.Changed` and a 30 s check loop, and evaluates the rules against preferences (from `UserProfileService`):

| Rule | Fires when | Bell item | Actions |
|---|---|---|---|
| **Long-running** | `Elapsed ≥ LongTimerWarningHours` (≠ 0) | "Timer running for 9h 12m: <task name>" | **Stop now** · **Open tracker** · **Dismiss** |
| **Idle** | Timer running and the idle detector reports ≥ `IdleWarningMinutes` (≠ 0) of no input, then the user comes back | "You were idle from 14:05 to 14:41" | **Stop at 14:05** (`StopAsync(endAt: idleStart)`) · **Keep** |

- **Dismiss / Keep** is remembered per timer (keyed by `StartDate`) in memory. *My call:* dismissing the long-running warning silences it **until the next multiple of the threshold**. With an 8 h threshold, dismissing at 8 h means it comes back at 16 h, not before. Keep on an idle warning applies only to that idle period; a new idle period raises a new item.
- The idle detector is a small JS module (`wwwroot/js/idle.js`). It watches `pointermove`, `keydown`, `wheel`, `touchstart` and `visibilitychange` (throttled), and reports `idleStart` once the idle period ends. **My call:** a hidden tab counts as idle only if no other Timinute tab is active. Tracking that across tabs is fiddly, so v2.5 treats each tab's activity independently and suppresses duplicate idle items when the user returns. A **known limitation**: working in another app without touching Timinute counts as idle. That is why the action is a choice and not automatic.
- **Browser notifications:** when enabled on this device and permission is `granted`, each new bell item also raises a `Notification` via JS interop, with a `tag` of rule + timer start so multiple open tabs collapse into one OS notification. Clicking it focuses the tab and opens the bell. When disabled, it does nothing.

### Bell popover (Aurora)

- **Build** the bell in the topbar on desktop. *(Correction: there is no bell markup in `Topbar.razor` today, only a `bell` icon in `AuroraIcons.razor`. The roadmap's "hidden bell" is stale.)* On mobile, add a bell entry to the slide-up overflow sheet, since the bottom tab bar has no room. The badge is the count of active items.
- The popover uses Aurora tokens and is keyboard reachable: `aria-expanded`, Escape closes it, focus returns to the bell, and items sit in a `role="list"`. It has an empty state ("Nothing needs your attention"). Arrival of a new item is announced through a new visually-hidden `aria-live="polite"` region in `MainLayout`. Today `aria-live` exists only in `Authentication.razor`, so there is no shared announcer to reuse.

```
 ┌──────────────────────────────────────┐
 │ Notifications                        │
 │ ──────────────────────────────────── │
 │ ⏱  Timer running for 9h 12m          │
 │    "Client X — API review"           │
 │    [Stop now] [Open tracker] [×]     │
 │ ──────────────────────────────────── │
 │ ☾  You were idle 14:05 – 14:41       │
 │    [Stop at 14:05]  [Keep]           │
 └──────────────────────────────────────┘
```

### Profile → Preferences card

There are three new rows, following the existing list-row treatment on mobile:
- *Warn when timer runs longer than* `[ 8.0 ] h` (0 = off)
- *Idle warning after* `[ 15 ] min` (0 = off)
- *Browser notifications on this device* `[toggle]`. Turning it on calls `Notification.requestPermission()`. If permission is denied, the toggle reverts and an inline hint explains how to re-enable it in browser settings.

All times shown are local (`.ToLocalTime()`, per CLAUDE.md).

## Aurora-native dialogs

Today `MainLayout` renders `<RadzenTheme Theme="material">` + `<RadzenDialog />`. There are 17 `DialogService` usages:
- 7 `OpenAsync<T>`: TrackedTaskScheduler ×2, TrackedTasks ×2, ProjectManager, MobileTabBar, Topbar.
- 5 `Confirm`: project delete, trash purge ×2, token revoke, tag force-delete.
- 5 `Close`: AddTrackedTask, AddProject, EditTrackedTaskForm ×2, AddTrackedTaskForm.

> Correction to the roadmap: it says the Tokens and AI-activity pages "already do" Aurora-native dialogs. They don't: `Tokens.razor` uses `DialogService.Confirm`. No Aurora modal component exists yet.

- Add `Client/Shared/AuroraModal.razor`: an overlay plus panel on Aurora tokens, with `role="dialog"`, `aria-modal`, `aria-labelledby`, a focus trap, Escape to close, return focus to the opener, and `prefers-reduced-motion` respected. It becomes a bottom sheet at ≤768 px, reusing the `MobileMoreSheet` patterns.
- Add an `AuroraDialogService` (singleton) whose API mirrors what the call sites use: `OpenAsync<TComponent>(title, parameters)` → `Task<object?>`, `Close(result)`, and `ConfirmAsync(message, title, okText, cancelText, danger: bool)`. A single `<AuroraDialogHost />` in `MainLayout` renders the stack. Migrate all call sites, and switch the form components' `DialogService.Close` calls to the new service.
- **`RadzenNotification` toasts stay** (CLAUDE.md allows Radzen for notifications). **Open question for the builder:** whether removing `<RadzenTheme>` unstyles the toasts. If it does, keep `RadzenTheme` loaded for toasts only; re-skinning toasts is out of scope. Remove `<RadzenDialog />`.

## Testing

- **Server unit tests (SQLite helper)** for `TimerAppService`. Cover: start/get/stop/discard; a second start → 409, including the unique-key race path; stop with `EndAt` before start, in the future, or omitted; a project soft-deleted mid-run → saved with null project and `ProjectCleared`; a foreign or whitespace or trailing-space `ProjectId` on start; and stop being atomic, so a failure while creating the task leaves the timer intact.
- **Ownership:** user B cannot see, stop or discard user A's timer, because every endpoint is user-scoped.
- **Integration tests** through `TiminuteApiFactory` for the 409/422 problem+json shapes and the preference range validation.
- **A test that a running timer never appears** in `/TrackedTask` search, the analytics endpoints or export (the B2 guarantee).
- **bUnit** for `TimerService` (refresh, legacy-migration path, 409 handling), `TimerNotificationService` rule evaluation with a fake clock (threshold, re-fire at multiples, dismiss memory, idle stop), the bell popover (empty state, actions, keyboard) and `AuroraModal` (focus/escape, result propagation).
- **Manual or `verify`-skill pass** in both themes: start in tab A, reload, close, open tab B, stop; idle warning; long-run warning with the threshold set to 0.1 h; browser-notification permission grant and deny; every migrated dialog in dark mode.
- **Reviewers before commit:** `ef-repository-reviewer` (new entity, service, controller) and `aurora-client-reviewer` (all client work).
